CROSS-ENGINE BENCHMARK HARNESS - MANUAL
========================================

This harness runs matched TPC-C, YCSB (A-F), and HTAP/CH-benCHmark workloads against
four storage engines - cMVBT, LeanStore, LeanStore's WiredTiger adapter, and PostgreSQL
(via BenchBase) - and produces one normalized manifest.csv plus a set of comparison
plots. It lives in this repo under scripts/ (compare_engines.py, setup_environment.py,
plot_compare.py, engines/*.py) and is designed to run identically on this workstation and
on the real 2x AMD EPYC 7742 server (2 NUMA nodes, 64 cores/128 threads per socket).

Directory layout it expects (all overridable via environment variables, see "PATHS"
below):

    <this repo>/scripts/...              orchestration scripts (you are here)
    ~/tx_tests/leanstore/                 LeanStore checkout + build/ (CMake)
    ~/tx_tests/wiredtiger/                WiredTiger checkout + cmake-build-debug/ (CMake)
    ~/tx_tests/benchbase/                 BenchBase checkout + target/benchbase-postgres/


1. REQUIREMENTS
----------------

- Linux, x86_64. `numactl` is REQUIRED (every benchmark subprocess runs under
  `numactl --cpubind=0 --membind=0` - there is no unpinned fallback, by design, so
  results are never accidentally cross-NUMA-node).
- Rust + Cargo (for cMVBT) - stable toolchain, whatever `cargo build --release` needs.
- CMake + a C++ toolchain with TBB, liburing, and the usual compression libs (snappy,
  zlib, bz2, lz4, zstd), for LeanStore + WiredTiger.
- A JDK (21 is verified working; BenchBase's pom.xml nominally wants 23 but the build is
  pinned down to 21 via -Dmaven.compiler.source/target) + Maven (via BenchBase's own
  ./mvnw wrapper, no separate Maven install needed).
- PostgreSQL server + client (`postgresql`, `postgresql-contrib`).
- Python 3 with pandas + matplotlib (only needed for plot_compare.py - a venv is set up
  automatically, see below).

All of this (except Rust/Cargo, which is assumed already installed since this is the
cMVBT repo itself) is installed/built by setup_environment.py - see section 2.


2. FIRST-TIME SETUP
--------------------

    python3 scripts/setup_environment.py

Run this yourself in an interactive terminal (not backgrounded) - it shells out to
`sudo apt-get install` and `sudo -u postgres psql` for the apt/PostgreSQL steps, and both
need to prompt you for a password / apt's own yes-no confirmation. It never tries to
elevate privileges silently.

It is idempotent: every step checks whether its target already exists/works before doing
anything, so re-running after a partial failure (e.g. you had to fix a missing dev
package) just picks up where it left off, without redoing finished steps.

What it does, in order:
  1. apt packages (see APT_PACKAGES in the script - cmake, libtbb-dev, libaio-dev,
     compression libs, liburing-dev, numactl, postgresql, postgresql-contrib).
  2. Builds WiredTiger from source (Release, -DENABLE_PYTHON=OFF) into
     ~/tx_tests/wiredtiger/cmake-build-debug (the directory name is a stale holdover from
     an old CLion default - it IS a Release build, not Debug; a build-type sanity check
     fails loudly if this ever regresses).
  3. Builds LeanStore's native + WiredTiger-adapter frontends (Release) into
     ~/tx_tests/leanstore/build, pointed at the WiredTiger build above via
     CMAKE_CXX_FLAGS/CMAKE_EXE_LINKER_FLAGS.
  4. Creates the `admin` (superuser) role and `benchbase` database in PostgreSQL.
  5. Clones BenchBase and builds it with its own ./mvnw wrapper. Before building, the
     script PATCHES BenchBase's pom.xml to strip out `com.spotify.fmt:fmt-maven-plugin` -
     see "MAVEN PLUGIN WORKAROUND" below. This step is idempotent too (safe to re-run,
     detects if the plugin block is already gone).
  6. Builds cMVBT itself (`cargo build --release`).
  7. Sets up the Python venv at scripts/.venv with pandas + matplotlib (needed only for
     plot_compare.py, not for running experiments).

Flags to skip individual steps (useful if you already have one piece set up, or are
re-running after fixing just one failure):

    --skip-apt --skip-wiredtiger --skip-leanstore --skip-postgres --skip-benchbase
    --skip-cmvbt --skip-venv

Example: `python3 scripts/setup_environment.py --skip-postgres --skip-benchbase`


MAVEN PLUGIN WORKAROUND (fmt-maven-plugin / similar failures)
---------------------------------------------------------------

If Maven fails while building BenchBase with an error about not being able to
download/resolve a plugin (observed on the server: `com.spotify.fmt:fmt-maven-plugin`),
this is a network/repository-access problem, not a code problem - Maven has to fetch a
plugin's descriptor before it can even decide whether to skip its goals, so this can't be
worked around with a `-Dfmt.skip=true`-style property.

setup_environment.py already handles this: right after cloning BenchBase, it strips the
plugin's whole <plugin>...</plugin> block out of pom.xml before running the build, so
Maven never attempts to resolve it. This is purely a code-style/static-analysis plugin -
removing it doesn't affect the produced benchbase.jar.

If you hit the SAME class of failure with a DIFFERENT plugin, add its
(groupId, artifactId) to `BENCHBASE_POM_PLUGINS_TO_STRIP` at the top of
scripts/setup_environment.py, then just re-run `python3 scripts/setup_environment.py` -
as long as the build never actually finished (target/benchbase-postgres doesn't exist
yet), it re-patches pom.xml and retries the Maven build automatically; no manual cleanup
needed.


REBUILDING ONE ENGINE MANUALLY (after editing its source, without the full script)
--------------------------------------------------------------------------------------

cMVBT:
    cargo build --release

LeanStore + WiredTiger adapter (from ~/tx_tests/leanstore, after WiredTiger's already
built once via setup_environment.py):
    cmake --build ~/tx_tests/leanstore/build --target tpcc ycsb wiredtiger_tpcc wiredtiger_ycsb --parallel $(nproc)

WiredTiger itself (rarely needed - only if you change WiredTiger's own source):
    cmake --build ~/tx_tests/wiredtiger/cmake-build-debug --target wiredtiger_shared wt --parallel $(nproc)

BenchBase (from ~/tx_tests/benchbase):
    ./mvnw -q clean package -P postgres -DskipTests \
        -Dmaven.compiler.source=21 -Dmaven.compiler.target=21 -Djava.version=21
    tar xzf target/benchbase-postgres.tgz -C target

Or just run `python3 scripts/compare_engines.py` without --skip-build - every engine's
own ensure_built() step already no-ops if nothing changed, so it's cheap to leave on by
default.


PATHS (environment variable overrides)
-----------------------------------------

Every path above has a single source of truth in scripts/engines/common.py, overridable
via environment variables if your checkout layout differs from the default:

    CMVBT_REPO            default: this repo's own root (self-detected - almost never
                           needs overriding)
    LEANSTORE_REPO         default: ~/tx_tests/leanstore
    WIREDTIGER_BUILD_DIR   default: ~/tx_tests/wiredtiger/cmake-build-debug
    BENCHBASE_HOME         default: ~/tx_tests/benchbase/target/benchbase-postgres
    PG_ROLE / PG_PASSWORD / PG_DATABASE   default: admin / password / benchbase

Set these before running any script, e.g.:

    LEANSTORE_REPO=/opt/leanstore python3 scripts/compare_engines.py ...


3. RUNNING EXPERIMENTS
------------------------

    python3 scripts/compare_engines.py [options]

This is the main entrypoint. It builds every requested engine (unless --skip-build),
then runs every requested workload x engine x thread-count x GC-variant combination,
appending one row per run to <output-root>/run_<timestamp>/manifest.csv as it goes (so a
partially-finished run still leaves usable data if interrupted).

Quick smoke test (fast, small data, 2 thread points):

    python3 scripts/compare_engines.py --tiny

Full run at the default (server) scale - WARNING: this is a lot of runs (engines x
workloads x threads x gc), potentially many hours; the banner printed at the start says
exactly how many runs and a lower-bound time estimate before anything starts:

    python3 scripts/compare_engines.py

Common ways to narrow scope for a faster/targeted run:

    python3 scripts/compare_engines.py --engines cmvbt,leanstore --workloads tpcc,ycsb_e
    python3 scripts/compare_engines.py --threads 1,4,16,64
    python3 scripts/compare_engines.py --gc on
    python3 scripts/compare_engines.py --workloads htap_q1,htap_q6

Options:

  --output-root DIR        where run_<timestamp>/ directories go (default:
                            comparison_results)
  --engines LIST            comma-separated subset of: cmvbt, leanstore, wiredtiger,
                            postgres (default: all four)
  --workloads LIST           comma-separated subset of: tpcc, ycsb_a..ycsb_f, htap_q1,
                            htap_q6 (default: all)
  --tiny                    small/fast smoke-test scale (1 warehouse, 10k YCSB records,
                            10s duration, threads=[1,2]) instead of the server scale
  --skip-build              skip each engine's build step (use if you already built
                            everything and just changed scale/workload/thread args)
  --threads LIST             comma-separated thread/terminal counts to sweep (default:
                            1,2,4,8,16,32,64,128 - one server socket's worth of SMT
                            threads; becomes 1,2 automatically with --tiny)
  --gc on|off|on,off         which GC variant(s) to run (default: both) - ignored for
                            engines with no working GC toggle (see section 5)
  --warehouses N             override TPC-C warehouse count (fixed across the whole
                            thread sweep - only terminals/threads vary)
  --tpcc-duration SECS
  --ycsb-records N
  --ycsb-duration SECS
  --theta FLOAT              YCSB Zipfian skew parameter
  --dram-gib FLOAT           LeanStore/WiredTiger buffer pool size (unused by
                            cmvbt/postgres)

Output layout per run:

    <output-root>/run_<timestamp>/
        manifest.csv                          one row per (workload, engine, threads, gc)
        <workload>/<engine>/threads_N/gc_X/    each run's raw output (stdout.log, CSVs,
                                               ssd image for leanstore/wiredtiger, etc.)


4. PLOTTING
-------------

    python3 scripts/plot_compare.py --run-dir <output-root>/run_<timestamp>

(or omit --run-dir to auto-pick the most recently modified run_* directory under
--results-root, default comparison_results). Needs the venv's pandas/matplotlib - either
activate it (`source scripts/.venv/bin/activate`) or invoke its interpreter directly
(`scripts/.venv/bin/python3 scripts/plot_compare.py ...`).

Every figure is written as both PDF and SVG into <run-dir>/plots/. Figures produced:

  tpcc_throughput_by_engine       TPC-C New-Order/sec, one bar per engine
  ycsb_throughput_by_engine       YCSB A-F ops/sec, grouped bars per workload x engine
  memory_by_engine                Peak RSS per workload x engine (PostgreSQL excluded -
                                  it's a multi-process server, no single-PID RSS is fair)
  summary_all_workloads            Every workload's primary metric, log-scaled, one chart
  threads_sweep_<workload>         Throughput vs. thread count, one line per engine (and
                                  per GC variant where applicable) - one file per workload
  gc_on_vs_off                     GC-on vs GC-off throughput, cmvbt/postgres only (the
                                  only two with a real toggle - see section 5)
  ycsb_e_scan_latency              YCSB-E scan-op latency (p50/p95/p99), all 4 engines
  cmvbt_tpcc_olap_scan_latency      cMVBT-only: its always-on concurrent OLAP-scan-sweep
                                  thread's latency vs. staleness/delay (HTAP-mode data
                                  specific to cMVBT, not comparable to the other 3
                                  engines' plain-OLTP TPC-C run in this harness)
  htap_interference                 OLTP throughput drop (%) under concurrent CH-benCHmark
                                  analytics (htap_q1/htap_q6) vs. plain TPC-C, per engine
  ch_query_latency                  CH-benCHmark Q1/Q6 analytical query latency, all 4
                                  engines

Most bar-chart-style figures (everything except the threads_sweep_* ones, which use every
thread point) are drawn from a "reference slice": the LARGEST thread count present in the
manifest, and gc="on" for engines that support toggling GC / "n/a" for the ones that
don't (never "off", so a bar chart never silently shows the GC-disabled number as if it
were the default). Every such figure's title says which thread count it's pinned to.


5. WHAT EACH ENGINE ACTUALLY SUPPORTS (read before interpreting results)
--------------------------------------------------------------------------

Not every engine supports every dimension identically - the harness is explicit about
this rather than papering over it:

- GC on/off: only cMVBT (real --gc flag) and PostgreSQL (via `autovacuum`, toggled with
  `ALTER SYSTEM` + `pg_reload_conf()`, no restart needed) have a genuine, working toggle.
  LeanStore's `--pgc` flag is DEAD CODE in this checkout (confirmed by grep: it's only
  read once, to report its own value into a profiling table - nothing in its B-tree
  actually branches on it), and the WiredTiger adapter has no equivalent at all (separate
  code path, doesn't touch LeanStore's MVCC machinery). Both always report gc="n/a" and
  run once per (workload, threads) regardless of --gc.

- HTAP/CH-benCHmark (htap_q1/htap_q6): CH-benCHmark has 22 standard analytical queries;
  only Q1 ("Pricing Summary Report") and Q6 ("Forecasting Revenue Change") are
  implemented across all 4 engines - these two happen to be the only pure-aggregation,
  no-join queries in the set, which is why they're the ones that could be ported
  everywhere without a lot of new work. cMVBT and PostgreSQL/BenchBase already had real
  implementations (cMVBT also implements Q4/Q5 internally, but those aren't part of this
  cross-engine comparison - only Q1/Q6 rows get read out of cMVBT's own output).
  LeanStore/WiredTiger's analyticalQuery() was a literal "TODO: implement CH analytical
  queries" stub before this harness added real Q1/Q6 bodies to it (see
  frontend/tpc-c/TPCCWorkload.hpp in the LeanStore checkout).

- Peak memory (peak_rss_mb): not tracked for PostgreSQL. Unlike the other three engines
  (where the benchmark process *is* the storage engine), BenchBase is only the JDBC
  client - the actual engine is Postgres's own multi-process server, and there's no
  single PID whose RSS is a fair analogue to the other engines' single-process peak RSS.

- NUMA pinning: every benchmark SUBPROCESS this harness spawns runs under
  `numactl --cpubind=0 --membind=0`. The PostgreSQL SERVER itself is a pre-existing
  system service, not spawned by this harness, so it is NOT NUMA-pinned by any of this -
  only the BenchBase JDBC client that talks to it is. Pinning the Postgres server itself
  would need a systemd unit override, outside this harness's scope.

- Low-warehouse-count TPC-C contention: at very small scale (e.g. --tiny's 1 warehouse),
  TPC-C throughput can drop sharply once the terminal/thread count exceeds the warehouse
  count - this is expected TPC-C lock contention (only one warehouse to spread load
  across), not a harness bug. Use --warehouses to scale data volume together with
  --threads if you want to avoid this at higher thread counts.


6. MANIFEST SCHEMA REFERENCE
-------------------------------

manifest.csv columns (scripts/engines/common.py::MANIFEST_HEADER):

    engine                cmvbt | leanstore | wiredtiger | postgres
    workload               tpcc | ycsb_a..ycsb_f | htap_q1 | htap_q6
    config_label            scale label ("tiny" or "server")
    threads                 thread/terminal count for this row
    gc_enabled               on | off | n/a
    duration_secs            requested run duration
    primary_metric_name       new_order_per_sec (tpcc/htap_q1/htap_q6) or ops_per_sec (ycsb)
    primary_metric_value
    peak_rss_mb               0 for postgres (see section 5)
    scan_p50_us / scan_p95_us / scan_p99_us / scan_count
                              scan/analytical-query latency percentiles (microseconds) -
                              populated for ycsb_e (scan ops), tpcc (cMVBT's own HTAP
                              scan-sweep only), and htap_q1/htap_q6 (CH-benCHmark query
                              latency); 0/blank elsewhere
    notes                     "FAILED ..." / "EXCEPTION: ..." on error, or an
                              engine-specific caveat (e.g. postgres's peak_rss note)
