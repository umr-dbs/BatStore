CROSS-ENGINE BENCHMARK HARNESS - MANUAL
========================================

This harness runs matched TPC-C, YCSB (A-F), and HTAP/CH-benCHmark workloads against eight
storage engines - BatStore (its own MVBTree, and a second libmdbx-backed comparison point),
LeanStore, LeanStore's WiredTiger adapter, PostgreSQL (via BenchBase), Umbra (umbra-db.com,
also via BenchBase - see engines/umbra_benchbase.py), and vWeaver_ermia
(ERMIA) built two ways: `-DCMAKE_BUILD_PARAM=Vweaver` (vWeaver's own "weaving" version-chain
compaction, engines/vweaver_ermia.py) and `-DCMAKE_BUILD_PARAM=Eval_skiplist` (the plain
frugal-list version chain with neither vWeaver nor its own compaction enabled, engines/
vweaver_ermia_frugal.py) - and produces one normalized manifest.csv plus a set of
comparison plots. It
lives in this repo under scripts/ (compare_engines.py, setup_environment.py,
plot_compare.py, engines/*.py) and is designed to run identically on this workstation and
on the real 2x AMD EPYC 7742 server (2 NUMA nodes, 64 cores/128 threads per socket).

Every sibling repo is cloned automatically (see section 2) into one workspace, rooted at
wherever you invoke setup_environment.py FROM - not a hardcoded path - so the exact same
scripts work starting from nothing, on any machine:

    <wherever you ran setup from>/tx_tests/
        leanstore/                 LeanStore checkout + build/ (CMake)
        wiredtiger/                 WiredTiger checkout + cmake-build-debug/ (CMake)
        benchbase/                   BenchBase checkout + target/benchbase-postgres/
        vWeaver_ermia/                 ERMIA checkout + build/ (Vweaver) + build_frugal/
                                          (Eval_skiplist) - one shared checkout, two builds
        batstore/                          only if umr-dbs/BatStore was reachable to clone
        scratch/<engine>/                 reused, wiped-before-every-run data directories
                                          (Umbra has no checkout here - it ships only as a
                                          Docker image, pulled directly; see section 2)


1. REQUIREMENTS
----------------

- Linux, x86_64. `numactl` is REQUIRED. Engines use benchmark NUMA node 0 by
  default; external BenchBase clients use the next available NUMA node so their CPU and
  heap do not compete with the database server. Override the client with
  `BENCHMARK_CLIENT_NUMA_NODE`.
- Rust + Cargo (for BatStore) - stable toolchain, whatever `cargo build --release` needs.
- CMake + a C++ toolchain with TBB, liburing, and the usual compression libs (snappy,
  zlib, bz2, lz4, zstd), for LeanStore + WiredTiger.
- clang/clang++ + libnuma-dev + libgoogle-glog-dev + libibverbs-dev, for vWeaver_ermia
  (ERMIA only builds with clang; the other three are linked unconditionally by its
  CMakeLists.txt even though this harness never exercises RDMA replication).
- A JDK (21 is verified working; BenchBase's pom.xml nominally wants 23 but the build is
  pinned down to 21 via -Dmaven.compiler.source/target) + Maven (plain `mvn`, not
  BenchBase's bundled ./mvnw wrapper - see section on why).
- PostgreSQL server + client (`postgresql`, `postgresql-contrib`).
- Docker, for Umbra (umbradb/umbra - it ships only as a Docker image, no native package;
  see section 2's step_umbra and engines/umbra_benchbase.py). Your user needs to be in
  the `docker` group (setup_environment.py adds it, but a fresh login/shell is needed
  before it takes effect - see step_umbra's docstring).
- Python 3 with pandas + matplotlib (only needed for plot_compare.py - a venv is set up
  automatically, see below).

All of this (except Rust/Cargo, which is assumed already installed since this is the
BatStore repo itself) is installed/built by setup_environment.py - see section 2.


2. FIRST-TIME SETUP
--------------------

    python3 scripts/setup_environment.py

Run this yourself in an interactive terminal (not backgrounded) - it shells out to
`sudo apt-get install` and `sudo -u postgres psql` for the apt/PostgreSQL steps, and both
need to prompt you for a password / apt's own yes-no confirmation. It never tries to
elevate privileges silently.

It is idempotent: every step checks whether its target already exists/works before doing
anything, so re-running after a partial failure (e.g. you had to fix a missing dev
package) just picks up where it left off, without redoing finished steps.

What it does, in order:
  1. apt packages (see APT_PACKAGES in the script - cmake, libtbb-dev, libaio-dev,
     compression libs, liburing-dev, numactl, postgresql, postgresql-contrib, maven,
     clang, libnuma-dev, libgoogle-glog-dev, libibverbs-dev).
  2. Clones (if missing) and builds WiredTiger from source (Release, -DENABLE_PYTHON=OFF)
     into <workspace>/wiredtiger/cmake-build-debug (the directory name is a stale holdover
     from an old CLion default - it IS a Release build, not Debug; a build-type sanity
     check fails loudly if this ever regresses).
  3. Clones (if missing) LeanStore, checks out the exact commit patches/leanstore.patch
     was generated against, applies that patch (CH-benCHmark Q1/Q6 analytical queries,
     YCSB-E/HTAP scan-latency instrumentation, New-Order-only counters - see section 5),
     then builds its native + WiredTiger-adapter frontends (Release) into
     <workspace>/leanstore/build.
  4. Reserves hugepages for vWeaver_ermia's node-memory pool (sudo sysctl -w
     vm.nr_hugepages=N, sized off common.Scale().dram_gib - see section 5).
  5. Clones (if missing) vWeaver_ermia, checks out the pinned commit patches/
     vweaver_ermia.patch was generated against, applies it (a dead include - see section
     5), applies patches/vweaver_ermia_frugal.patch (fixes two upstream bugs that only
     affect the frugal-list build below - a no-op for this one, see section 5), generates
     dbcore/burt-hash.cpp via patches/vweaver_burt_hash_gen.py (a Python 3 port of
     upstream's Python-2-only generator), then builds `ermia_SI` (CC=clang CXX=clang++,
     -DCMAKE_BUILD_PARAM=Vweaver) into <workspace>/vWeaver_ermia/build.
  6. Builds a SECOND `ermia_SI` from that same checkout (CC=clang CXX=clang++,
     -DCMAKE_BUILD_PARAM=Eval_skiplist - "just frugal lists", no vWeaver) into
     <workspace>/vWeaver_ermia/build_frugal - see engines/vweaver_ermia_frugal.py and
     section 5 for why this needed patches/vweaver_ermia_frugal.patch to even link.
  7. Creates the `admin` (superuser) role and `benchbase` database in PostgreSQL, applies
     a benchmark profile, and constrains the service to a fixed memory budget. The default
     budget is 8 GiB (`POSTGRES_MEMORY_BUDGET_GIB` overrides it): shared_buffers=25%,
     effective_cache_size=75%, work_mem=4MB, maintenance_work_mem=256MB, JIT off,
     random_page_cost=1.1, checkpoint_timeout=30min, max_wal_size=16GB, and swap disabled.
  8. Clones (if missing) BenchBase and builds it with plain `mvn` (not the bundled
     ./mvnw). Before building, the script PATCHES BenchBase's pom.xml to strip out
     `com.spotify.fmt:fmt-maven-plugin` - see "MAVEN PLUGIN WORKAROUND" below. This step
     is idempotent too (safe to re-run, detects if the plugin block is already gone).
  9. Installs Docker (if missing), adds you to the `docker` group, and pulls the pinned
     umbradb/umbra image (common.UMBRA_IMAGE) - see engines/umbra_benchbase.py, which
     starts/stops one throwaway container per benchmark run rather than a checkout+build
     this script performs itself (Umbra has no native package).
  10. Attempts to clone BatStore itself (umr-dbs/BatStore) into the workspace; if that
     fails (e.g. the repo is private and you don't have access here), falls back to
     building the checkout this script is already part of instead - see "BATSTORE_REPO
     RESOLUTION" below for exactly how this is decided and a gotcha to know about.
  11. Sets up the Python venv at scripts/.venv with pandas + matplotlib (needed only for
     plot_compare.py, not for running experiments).

By default the setup removes and freshly clones every setup-managed checkout under
WORKSPACE_ROOT. Pass `--reuse-checkouts` only when you intentionally want incremental
builds. vWeaver and its hugepage setup remain excluded unless `--full` is passed.

Flags to skip individual steps:

    --skip-apt --skip-wiredtiger --skip-leanstore --skip-hugepages --skip-vweaver
    --skip-vweaver-frugal --skip-postgres --skip-benchbase --skip-umbra --skip-batstore
    --skip-venv --skip-postgres-tmpfs

Example: `python3 scripts/setup_environment.py --skip-postgres --skip-benchbase`

To reapply only PostgreSQL's tuning, runtime cgroup limits, and tmpfs setup after a reboot
or a profile change, run `python3 scripts/setup_environment.py --postgres-only`.

PostgreSQL tmpfs relocation now runs by default. It stops/restarts the actual PostgreSQL
service and preserves the original PGDATA as `<PGDATA>.diskbackup`; read
step_postgres_tmpfs's docstring before using it on a server you care about. Use
`--skip-postgres-tmpfs` to opt out (PostgreSQL benchmark runs will then refuse to start if
PGDATA is not independently tmpfs-backed).


MAVEN: mvn, not mvnw
-----------------------

BenchBase is built with plain `mvn clean package ...` (no `-q`), not its own bundled
`./mvnw` wrapper - so the full build output streams straight to this console instead of
being interleaved with (or hidden by) the wrapper's own download/bootstrap noise, and so
build errors (missing plugins, dependency failures) are visible immediately instead of
buried in wrapper output. Requires a system `maven` install (see APT_PACKAGES).


MAVEN PLUGIN WORKAROUND (fmt-maven-plugin / similar failures)
---------------------------------------------------------------

If Maven fails while building BenchBase with an error about not being able to
download/resolve a plugin (observed on the server: `com.spotify.fmt:fmt-maven-plugin`),
this is a network/repository-access problem, not a code problem - Maven has to fetch a
plugin's descriptor before it can even decide whether to skip its goals, so this can't be
worked around with a `-Dfmt.skip=true`-style property.

setup_environment.py already handles this: right after cloning BenchBase, it strips the
plugin's whole <plugin>...</plugin> block out of pom.xml before running the build, so
Maven never attempts to resolve it. This is purely a code-style/static-analysis plugin -
removing it doesn't affect the produced benchbase.jar.

If you hit the SAME class of failure with a DIFFERENT plugin, add its
(groupId, artifactId) to `BENCHBASE_POM_PLUGINS_TO_STRIP` at the top of
scripts/setup_environment.py, then just re-run `python3 scripts/setup_environment.py` -
as long as the build never actually finished (target/benchbase-postgres doesn't exist
yet), it re-patches pom.xml and retries the Maven build automatically; no manual cleanup
needed.


BATSTORE_REPO RESOLUTION (read this if BatStore-related runs seem to use stale code)
----------------------------------------------------------------------------------

`scripts/engines/common.py` resolves `BATSTORE_REPO` like this: if
`<workspace>/batstore/Cargo.toml` exists, use `<workspace>/batstore`; otherwise fall back to
this file's own grandparent directory (i.e. the checkout this script is already part of -
self-referential, so it's automatically correct without any clone). The `Cargo.toml`
check is meant to distinguish "a real clone happened" from "nothing's there yet" - but it
can't distinguish a REAL, up-to-date clone from any OTHER directory that merely happens to
contain a Cargo.toml (e.g. a stale manual copy from before this automation existed).

If you have an old, non-git directory at `<workspace>/batstore` from before this clone
automation existed, it will shadow the self-referential fallback and silently get used
instead of your actively-developed checkout - any Rust source changes you make in the
"real" repo won't be reflected in benchmark runs. Either delete that stale directory, or
set the `BATSTORE_REPO` environment variable explicitly to override auto-detection:

    BATSTORE_REPO=/path/to/the/repo/you/are/editing python3 scripts/compare_engines.py ...

If the BatStore clone is unavailable, the self-referential fallback engages and builds
from the checkout containing these scripts. When both a workspace clone and a separate
development checkout exist, ensure the workspace clone contains the revision you intend
to benchmark or set `BATSTORE_REPO` explicitly.


3. RUNNING EXPERIMENTS
------------------------

    python3 scripts/compare_engines.py [options]

This is the main entrypoint. It builds every requested engine (unless --skip-build),
then runs every requested workload x engine x thread-count x GC-variant combination,
appending one row per run to <output-root>/run_<timestamp>/manifest.csv as it goes (so a
partially-finished run still leaves usable data if interrupted).

Quick smoke test (fast, small data, threads=[2,4]):

    python3 scripts/compare_engines.py --tiny

Full run at the default (server) scale - WARNING: this is a lot of runs (engines x
workloads x threads x gc), potentially many hours; the banner printed at the start says
exactly how many runs and a lower-bound time estimate before anything starts:

    python3 scripts/compare_engines.py

Common ways to narrow scope for a faster/targeted run:

    python3 scripts/compare_engines.py --engines batstore,leanstore --workloads tpcc,ycsb_e
    python3 scripts/compare_engines.py --threads 2,4,16,64
    python3 scripts/compare_engines.py --gc on
    python3 scripts/compare_engines.py --workloads htap_q1,htap_q6

Options:

  --output-root DIR        where run_<timestamp>/ directories go (default:
                            comparison_results)
  --engines LIST            comma-separated subset of: batstore, leanstore, wiredtiger,
                            postgres, umbra, vweaver_ermia, vweaver_ermia_frugal, libmdbx
                            (default: all eight)
  --workloads LIST           comma-separated subset of: tpcc, ycsb_a..ycsb_f, htap_q1,
                            htap_q6, htap_q1_variant, htap_q6_variant, s_htap. The query
                            variants are selectable but excluded from the default run.
  --ycsb-payload MODE        standard (default: 10 fields x 100 bytes) or u64 (one
                            8-byte value), applied consistently to every YCSB engine
  --ycsb-key-only            only establish key/visibility matches; by default point
                            reads and scans consume the selected payload's bytes
  --batstore-ycsb-mode MODE     BatStore only: atomic (default) uses the one-operation
                            commit-before-publish path; transaction uses the ordinary
                            registered transaction lifecycle
  --tiny                    small/fast smoke-test scale (1 warehouse, 10k YCSB records,
                            10s duration, threads=[2,4]) instead of the server scale
  --skip-build              skip each engine's build step (use if you already built
                            everything and just changed scale/workload/thread args)
  --threads LIST             comma-separated thread/terminal counts to sweep (default:
                            2,4,8,16,32,64,128 - one server socket's worth of SMT
                            threads; becomes 2,4 automatically with --tiny)
  --htap-cpu-budget N        BatStore HTAP only: CPU capacity shared by OLTP terminals
                            and the Q1/Q6 parallel scan pool (default: largest --threads
                            value). At each point the pool gets max(0, N - terminals)
                            workers; a result below 2 selects the sequential scan path.
  --scan-pool-workers N      BatStore only: override the dynamic HTAP allocation with one
                            fixed pool size at every point. Zero disables parallel scans.
                            When omitted, YCSB continues using its own automatic sizing.
  --gc on|off|on,off         which GC variant(s) to run (default: both) - ignored for
                            engines with no working GC toggle (see section 5)
  --warehouses N             override TPC-C warehouse count (fixed across the whole
                            thread sweep - only terminals/threads vary)
  --tpcc-duration SECS
  --ycsb-records N
  --ycsb-duration SECS
  --theta FLOAT              YCSB Zipfian skew parameter
  --dram-gib FLOAT           LeanStore/WiredTiger buffer pool size, and vWeaver_ermia's
                            -node_memory_gb (unused by batstore/postgres/libmdbx). Omit it and
                            this auto-computes PER WORKLOAD/THREADS POINT, proportional to
                            that point's own estimated dataset size (common.py::
                            dram_gib_for - ~4x a rough ~100MB/warehouse or ~1KB/record
                            estimate), capped at this machine's own NUMA-node-safe ceiling
                            (common.py::default_dram_gib, which scales between the 32GB
                            workstation and the real ~500GB server automatically). This
                            matters for more than just avoiding eviction: an oversized
                            buffer pool's own per-frame bookkeeping is real resident memory
                            proportional to dram_gib itself, independent of how much data
                            is actually loaded - sizing it to the workload instead of a
                            flat machine-wide number is what keeps peak_rss_mb in
                            manifest.csv representative of genuine usage rather than
                            dominated by that overhead. Pass --dram-gib explicitly to pin
                            one fixed value across every workload/threads point instead
                            (applied unchanged, no auto-sizing).

Output layout per run:

    <output-root>/run_<timestamp>/
        manifest.csv                          one row per (workload, engine, threads, gc)
        <workload>/<engine>/threads_N/gc_X/    each run's raw output (stdout.log, CSVs)

Note the engine's actual on-disk DATA (LeanStore/WiredTiger's ssd image, libmdbx's
environment, ERMIA's log dir) does NOT live under this per-combo tree - see section 4.


4. IN-MEMORY ONLY: TMPFS-BACKED, WIPED-BEFORE-EVERY-RUN DATA DIRECTORIES
--------------------------------------------------------------------------

Every engine's own on-disk DATA (not its small result artifacts - those still live under
the per-combo tree above) lives at a FIXED, tmpfs-backed path, entirely deleted and
recreated before every single run:

    <SCRATCH_ROOT>/<engine>_data/     (leanstore, wiredtiger, libmdbx, batstore)
    <SCRATCH_ROOT>/vweaver_ermia_log/
    <SCRATCH_ROOT>/vweaver_ermia_frugal_log/

SCRATCH_ROOT (env var, default /dev/shm/batstore_bench_scratch) MUST be tmpfs -
common.py::fresh_scratch_dir checks this on every call and sys.exit's loudly if it isn't,
rather than silently falling back to a real disk-backed directory. This is what makes
"in-memory only" an actual guarantee rather than a hope: LeanStore/WiredTiger/libmdbx/
vWeaver_ermia all still perform real file I/O (page eviction, WAL flush, mmap writeback)
regardless of buffer-pool/cache sizing - backing that I/O with tmpfs (RAM) is the only way
to ensure none of it ever reaches a physical disk. BatStore's own WAL is forced ON,
unconditionally, in every workload this harness drives (see batstore.py) and written to this
same tmpfs-backed scratch dir - LeanStore's WAL (baked into its B-tree core,
WALMacros.hpp) can't be disabled either, so leaving BatStore's off by default would compare a
durable-logging engine against a non-durable one; forcing it on everywhere means the only
overhead this adds anywhere is genuine serialization/fsync cost, never real disk I/O. See
section 5 below for PostgreSQL, which this harness does NOT control the storage of.

Also still sizes `--dram-gib` (LeanStore/WiredTiger's buffer pool cap - see section 3's
--dram-gib entry) comfortably above each workload's own working set, computed fresh per
workload/threads point rather than one flat number: even against tmpfs, an undersized
buffer pool still pays real eviction/reload CPU overhead simulating disk pressure that
isn't there, which would confound an in-memory-only comparison - and an OVERSIZED one
inflates peak_rss_mb with buffer-pool bookkeeping that has nothing to do with the
workload's actual memory use (see common.py::dram_gib_for's docstring).

Disk usage (RAM usage, really) never accumulates across a long thread/workload sweep the
way a fresh uniquely-named directory per sweep point would - only the CURRENT experiment's
data ever exists at all, never every prior one's too. The tradeoff: you can't go back and
inspect e.g. run #47's raw ssd image after run #48 has started (it's been wiped) - only
the small per-combo artifacts (stdout.log, result CSVs) survive for later inspection.


5. WHAT EACH ENGINE ACTUALLY SUPPORTS (read before interpreting results)
--------------------------------------------------------------------------

Not every engine supports every dimension identically - the harness is explicit about
this rather than papering over it:

- WAL: BatStore's WAL is forced ON unconditionally (see section 4) to match LeanStore, whose
  WAL (baked into its B-tree core) can't be disabled either. The WiredTigerAdapter this
  harness drives (frontend/shared/WiredTigerAdapter.hpp) originally opened its connection
  with `log=(enabled=false)` - WiredTiger's own WAL silently OFF, an asymmetry against
  both of those - patches/leanstore.patch now flips it to `log=(enabled=true)` so all
  three durability-capable engines are on equal footing. libmdbx has no separate WAL
  concept (its own copy-on-write meta-page double-buffering is its durability mechanism);
  PostgreSQL's WAL is always on and can't be disabled either.

- GC on/off: BatStore (real --gc flag), PostgreSQL (via `autovacuum`, toggled with
  `ALTER SYSTEM` + `pg_reload_conf()`, no restart needed), and vWeaver_ermia (real
  `-enable_gc` flag - gates actual version-chain reclamation in dbcore/sm-alloc.cpp and
  dbcore/sm-oid.cpp, confirmed by reading both call sites, not just its own README) all
  have a genuine, working toggle. LeanStore's `--pgc` flag is DEAD CODE in this checkout
  (confirmed by grep: it's only read once, to report its own value into a profiling table
  - nothing in its B-tree actually branches on it), and the WiredTiger adapter has no
  equivalent at all (separate code path, doesn't touch LeanStore's MVCC machinery).
  libmdbx (like any real path-copying/CoW MVCC store) reclaims old pages once no reader
  references them, with no separate toggle either. Umbra has an `autovacuum` GUC that
  *reads* as on/off like PostgreSQL's, but this build refuses to change it at all - both
  `ALTER SYSTEM SET autovacuum = ...` ("ALTER SYSTEM not implemented yet") and plain `SET
  autovacuum = ...` ("cannot change configuration parameter") were tried directly against
  a live umbra-server and both failed - so it's treated the same as LeanStore/WiredTiger/
  libmdbx here. LeanStore/WiredTiger/libmdbx/Umbra always report gc="n/a" and run once per
  (workload, threads) regardless of --gc.

  For PostgreSQL, each run verifies the live value before loading. GC-off also terminates
  any autovacuum worker left from the preceding run and waits for it to disappear; GC-on
  restores `autovacuum=on`. PostgreSQL can still launch an emergency anti-wraparound
  vacuum while autovacuum is off, but freshly recreated benchmark tables are nowhere near
  the transaction-age threshold where that exception applies. At process exit, the
  harness restores `autovacuum=on` if the final PostgreSQL point used GC-off.

- PostgreSQL durability: every PostgreSQL point runs in the benchmark performance mode
  `fsync=off`, `synchronous_commit=off`, and `full_page_writes=off`. These are applied and
  live-verified before every run and recorded in that point's `server_config.json`. This
  is intentionally unsafe for real data; the harness recreates its benchmark tables.

- HTAP/CH-benCHmark (htap_q1/htap_q6): these names now execute the SQL predicates from
  pinned BenchBase commit 33c00473807ebd49304d114a6d769d2d2b2bbb34 exactly: Q1 uses
  `ol_delivery_d > 2007-01-02`, and Q6 uses the half-open 1999-01-01..2020-01-01 date
  window plus inclusive quantity 1..100000. BatStore applies its delivery-date zone map
  to both canonical queries. Because the loaders use present-day timestamps, exact Q6
  normally has an empty input today; that is also what PostgreSQL/BenchBase executes.
  The former engine-local predicates remain selectable as htap_q1_variant and
  htap_q6_variant. They intentionally preserve the old behavior and are not suitable for
  cross-engine result comparisons (PostgreSQL's variant aliases equal canonical because
  it already ran the BenchBase SQL).

  CH-benCHmark has 22 standard analytical queries;
  only Q1 ("Pricing Summary Report") and Q6 ("Forecasting Revenue Change") are
  implemented across the engines that support this at all - these two happen to be the
  only pure-aggregation, no-join queries in the set, which is why they're the ones that
  could be ported everywhere without a lot of new work. BatStore and PostgreSQL/BenchBase
  already had real implementations (BatStore also implements Q4/Q5 internally, but those
  aren't part of this cross-engine comparison - only Q1/Q6 rows get read out of BatStore's
  own output). LeanStore/WiredTiger's analyticalQuery() was a literal "TODO: implement CH
  analytical queries" stub before this harness added real Q1/Q6 bodies to it (see
  frontend/tpc-c/TPCCWorkload.hpp in the LeanStore checkout). libmdbx got the same
  treatment in src/bat_bench/mdbx_tpcc.rs (`mdbx_q1`/`mdbx_q6`, a libmdbx port of
  `bat_bench::tpch_queries::q1`/`q6` against its own `Transaction<RO>`/cursor API, plus one
  OLAP thread rotating them - see that module's docs). Both vWeaver_ermia variants got it
  too, via patches/vweaver_ermia_chbenchmark.patch (`RunChQ1`/`RunChQ6` in ERMIA's own
  benchmarks/tpcc.cc, a real `ORDER_LINE` table scan against ERMIA's own transaction/Scan
  API, plus the requested number of dedicated `tpcc_bench_runner::StartHtapThread` OLAP
  threads - the same "N OLTP + M OLAP" convention as every other engine here) - see
  engines/vweaver_ermia.py's
  module docstring for the full writeup, including a real heap-corruption bug (an
  unbounded table scan overflowing str_arena's fixed 128MB reservation, silent in a
  Release build) hit and fixed during development. Applies identically to both
  CMAKE_BUILD_PARAM variants - no `#ifdef HYU_VWEAVER`/`HYU_SKIPLIST` branching in that
  patch at all.

- libmdbx's single-writer model: unlike every other engine here, libmdbx (like LMDB)
  allows only ONE read-write transaction active process-wide at a time - there is no
  possible write-write race the way BatStore's OSIC or a real distributed-lock MVCC engine
  has. Any workload with a write component (update/insert/read-modify-write for YCSB;
  New-Order/Payment/Delivery for TPC-C) will show throughput fundamentally bounded by that
  single-writer serialization as thread count grows. This is a genuine, expected
  characteristic of path-copying/CoW MVCC to surface honestly, not a wrapper bug - and it
  means libmdbx's TxnOutcome has no "Conflict" case a concurrent writer can trigger; that
  outcome is kept only for the same defensive "row unexpectedly missing" checks the
  original TPC-C code has (which would indicate a genuine data/scale bug, not a race).

- vWeaver_ermia (ERMIA) build status: BUILDS AND RUNS. After fixing missing
  libgoogle-glog-dev/libibverbs-dev packages, a dead `#include <sys/vtimes.h>`, and an
  off-by-one start barrier that otherwise waits forever, and TPC-C creating one extra
  unrequested worker (the source fixes in patches/vweaver_ermia.patch), and generating
  dbcore/burt-hash.cpp - a
  gitignored build artifact upstream normally produces via `python2 dbcore/burt-hash.py`
  (no python2 on this system; setup_environment.py runs a Python 3 port instead, see
  patches/vweaver_burt_hash_gen.py) - `-DCMAKE_BUILD_PARAM=Vweaver` builds `ermia_SI`
  cleanly. One operational requirement: ermia_SI preallocates its whole working set up
  front via `mmap(..., MAP_HUGETLB)` (dbcore/sm-alloc.cpp::prepare_node_memory, sized by
  `-node_memory_gb`) and crashes immediately (uncaught os_error) if the kernel has no
  hugepages reserved - setup_environment.py's step_vweaver_hugepages() reserves them
  (sudo sysctl, prompts for your password like the apt step).
  An EARLIER version of this pin/patch was accidentally generated against a divergent
  fork (Rudeus/vWeaver_ermia) instead of the repo actually specified
  (SNU-DBXLab-papers/vWeaver_ermia) - that fork has a real masstree scan() overload-arity
  bug this repo does NOT have; the wrong pin/patch/docstring describing it have all been
  replaced with ones verified against the correct upstream.
  A reported "vWeaver doesn't work" was root-caused to the `os_error` above - verified
  IDENTICAL for every CMAKE_BUILD_PARAM (prepare_node_memory() doesn't branch on
  HYU_VWEAVER/HYU_SKIPLIST at all), i.e. plain insufficient reserved hugepages, not a
  vWeaver-specific bug. `ermia_SI` itself builds and starts identically either way.

- vweaver_ermia_frugal (ERMIA, "just frugal lists") build status: same checkout as
  vweaver_ermia, built instead with `-DCMAKE_BUILD_PARAM=Eval_skiplist` (`-DHYU_SKIPLIST`,
  no `-DHYU_VWEAVER`) into its own vWeaver_ermia/build_frugal - the plain frugal-list
  version chain this fork's own CMakeLists.txt offers, with neither vWeaver's own
  "weaving" compaction nor the Eval_frugal variant's HYU_VWEAVER-dependent stat collection
  enabled. Unlike the Vweaver build, this one does NOT build out of the box: `-DHYU_SKIPLIST`
  alone calls `MM::deallocate_skiplist()` (dbcore/sm-alloc.h/sm-oid.cpp/sm-oid.h) which was
  declared and called but never defined anywhere upstream - a hard link error - and
  `MM::gc_version_chain()`'s dedicated `#elif defined(HYU_SKIPLIST)` branch (which would
  recycle a reclaimed version's Lv-pointer array) was present in dbcore/sm-alloc.cpp but
  commented out, silently falling through to the plain-masstree `#else` branch instead (a
  memory leak, not a crash). patches/vweaver_ermia_frugal.patch fixes both by restoring
  the vendor's own disabled reference code for the GC branch (renamed to the real
  `gc_version_chain` entry point actually called from sm-oid.cpp) and adding
  `deallocate_skiplist()` following the same recycle-into-`tls_free_object_pool` pattern
  `deallocate()` already uses. Entirely guarded by `#ifdef HYU_SKIPLIST` - a no-op for the
  plain Vweaver build - so it's applied unconditionally onto the one shared checkout.
  Builds cleanly via setup_environment.py's step_vweaver_ermia_frugal().
  KNOWN ISSUE (found once this machine had enough hugepages to actually sustain a real
  multi-second run, not just start one - see vweaver_ermia's own hugepages note above):
  this build reliably SIGSEGVs a few seconds into ANY real TPC-C workload with GC enabled
  (reproduces on plain "tpcc", not specific to htap_q1/htap_q6), consistently inside
  `MM::gc_version_chain` -> `sm_oid_mgr::oid_get_version_skiplist_from_ver` during a normal
  New-Order/Payment update (a near-null pointer read off `Object::GetSentinel()`, i.e. some
  object reachable from an active version chain ends up without the sentinel array every
  other object on that chain has). This is a genuine concurrency bug in the restored
  HYU_SKIPLIST GC code above (patches/vweaver_ermia_frugal.patch) or in the vendor's
  broader skip-list machinery it depends on (SubmitSkipListChain/SentinelOverwrite in
  dbcore/sm-oid.cpp, not yet root-caused) - not something patches/
  vweaver_ermia_chbenchmark.patch's Q1/Q6 additions touch or introduced (confirmed: crashes
  identically with --enable-chbenchmark on or off). Until this is root-caused, this engine
  variant should be treated as NOT reliably usable for write-heavy/concurrent comparison
  runs. Disabling GC lets a one-worker smoke test complete, but a two-worker test can hang
  after loading, so `--gc off` is not a general repair.

- Umbra (umbra-db.com, engines/umbra_benchbase.py): TUM's db.in.tum.de research OLTP+OLAP
  engine, driven through the exact same BenchBase `<type>POSTGRES</type>` JDBC target as
  PostgreSQL - confirmed directly (DDL with FKs/composite PKs/CHAR/DECIMAL/TIMESTAMP,
  prepared statements, JDBC-style batch inserts, multiple logical databases via `CREATE
  DATABASE`) that its wire-protocol surface covers everything BenchBase's tpcc/ycsb/
  chbenchmark DDL actually uses, before writing the wrapper. Ships ONLY as a Docker image
  (umbradb/umbra - no native package/tarball), so unlike every source-built engine here,
  setup_environment.py's step_umbra just installs Docker and pulls the pinned image; the
  wrapper itself starts/stops one throwaway container per run() (bind-mounted onto a
  fresh tmpfs scratch dir, NUMA-pinned via `docker run --cpuset-cpus/--cpuset-mems`,
  verified against the live container's cgroup the same way the PostgreSQL wrapper
  verifies the postmaster). Listens on port 5433 (not 5432 - PostgreSQL's own cluster
  service already owns that port on the same machine), default role/password `postgres`/
  `postgres` (set by the image's own docker-entrypoint.sh), database `benchbase` (created
  fresh every run via `psql`, same as PostgreSQL's own one-time setup).
  DURABILITY: this build (v0.2, "internal evaluation" license) exposes NO working way to
  relax fsync/synchronous_commit/full_page_writes in software - confirmed directly that
  `ALTER SYSTEM` is simply unimplemented and plain `SET` refuses every one of those GUCs,
  and there's no command-line flag either (umbra-server --help lists only address/port/
  createdb/readonly/SSL-cert options). So "memory-only" for Umbra means ONLY the
  tmpfs-backed scratch directory every non-PostgreSQL engine already gets (section 4) -
  its own fsync calls still happen, they just land on RAM, never real disk. This also
  means compare_engines_new.py's NO_DURABILITY mode (real disk, relying on each engine's
  own fsync-off) has no safe equivalent for Umbra: every point is reported SKIPPED there
  instead of silently paying real-disk fsync cost under a flag whose whole point is "no
  durability cost" - use compare_engines.py (tmpfs-backed) for Umbra numbers.

- Peak memory (peak_rss_mb): the column name is retained for compatibility, but PostgreSQL
  reports the peak cgroup-v2 `memory.current` charge for its dedicated systemd service.
  That includes anonymous memory, shared mappings, and charged page cache without
  double-counting shared pages across PostgreSQL processes. If cgroup v2 is unavailable,
  it falls back to summed server process-tree RSS. The JDBC client is excluded. Each row's
  exact method is recorded in `memory_source`, and PostgreSQL writes `memory_stats.json`
  with the `memory.stat` breakdown at the peak. Other single-process engines report VmHWM.

- NUMA pinning: engine subprocesses use benchmark node 0 by default. Setup gives the
  PostgreSQL systemd service matching `AllowedCPUs` and `AllowedMemoryNodes` constraints,
  while its external BenchBase JDBC client uses the next NUMA node when available. Umbra's
  server is spawned by this harness (a fresh container per run), but numactl in front of `docker run`
  itself would only pin the short-lived CLI invocation, not the actual server process the
  Docker daemon spawns - so it's pinned instead via the container's own cgroup
  (`--cpuset-cpus`/`--cpuset-mems`), verified against the live container's
  /proc/<pid>/status after start.

- In-memory only (section 4), PostgreSQL, and Umbra: SCRATCH_ROOT's tmpfs guarantee covers
  LeanStore/WiredTiger/libmdbx/vWeaver_ermia because this harness owns their data
  directories directly, and Umbra the same way (its container's /var/db bind mount points
  at a fresh tmpfs scratch dir every run - see the Umbra bullet above). The default
  setup's PostgreSQL tmpfs step stops the real PostgreSQL service, moves its actual
  PGDATA onto tmpfs (preserving the original on real disk as `<PGDATA>.diskbackup`), and
  restarts it. With `--skip-postgres-tmpfs`, PostgreSQL's storage stays wherever it already was
  (almost certainly real disk) and is NOT part of the in-memory-only guarantee the other
  four engines now have. One caveat: tmpfs is volatile, so a reboot wipes it and
  PostgreSQL will fail to start until you run setup with `--postgres-only` (it
  restores from the `.diskbackup` automatically - there's no systemd-level auto-restore on
  boot, by design, see the docstring). The PostgreSQL wrapper verifies the live PGDATA
  filesystem and refuses to benchmark unless it is tmpfs-backed.

- Low-warehouse-count TPC-C contention: at very small scale (e.g. --tiny's 1 warehouse),
  TPC-C throughput can drop sharply once the terminal/thread count exceeds the warehouse
  count - this is expected TPC-C lock contention (only one warehouse to spread load
  across), not a harness bug. Use --warehouses to scale data volume together with
  --threads if you want to avoid this at higher thread counts. Similarly, at very small
  customers-per-district counts, TPC-C's "by last name" customer lookups (Payment/
  Order-Status, ~60% of those transactions) can have a high miss rate purely because the
  ~1,000 possible last-name codes outnumber the loaded customer pool - also expected, not
  a bug (verified identical behavior between BatStore's own TPC-C driver and the new libmdbx
  one at the same tiny scale).


6. HOW LIBMDBX WAS ADDED (src/bat_bench/mdbx_ycsb.rs, mdbx_tpcc.rs)
------------------------------------------------------------------------

A second, independent storage backend inside BatStore itself, using the `libmdbx` Rust crate
(a path-copying/copy-on-write B+Tree) instead of BatStore's own version-chain MVBTree, run
through the SAME standard TPC-C/YCSB A-F workloads for a genuine architecture-vs-
architecture MVCC comparison. Gated behind the `mdbx-backend` Cargo feature (optional -
not every build needs a second storage engine):

    cargo build --release --features mdbx-backend

This reuses BatStore's existing schema/row/key/WAL-codec layer entirely as-is (`TpccRow`/
`YcsbRow`, their `WalPayload` byte encoders, `TpccConfig`/`YcsbConfig`, every bit-packed
`u64` key-builder function) - that layer was already fully storage-engine-agnostic. Only
the transaction logic and driver loop are reimplemented against libmdbx's
`Transaction<RO|RW>` API, since there's no trait boundary in this codebase between
BatStore's own tree and its business logic - `mdbx_ycsb.rs`/`mdbx_tpcc.rs` are parallel
files, not a generic backend swapped into the existing drivers. New CLI subcommands
(`mdbx_ycsb`, `mdbx_tpcc`) mirror the existing `ycsb`/`tpcc` subcommands' positional-arg
order wherever the concept overlaps, dropping every knob that has no libmdbx equivalent
(BatStore's own GC/root-index/WAL/affinity knobs).


7. REBUILDING ONE ENGINE MANUALLY (after editing its source, without the full script)
--------------------------------------------------------------------------------------

BatStore:
    cargo build --release
    cargo build --release --features mdbx-backend    # to also get mdbx_ycsb/mdbx_tpcc

LeanStore + WiredTiger adapter (from <workspace>/leanstore, after WiredTiger's already
built once via setup_environment.py):
    cmake --build <workspace>/leanstore/build --target tpcc ycsb wiredtiger_tpcc wiredtiger_ycsb --parallel $(nproc)

WiredTiger itself (rarely needed - only if you change WiredTiger's own source):
    cmake --build <workspace>/wiredtiger/cmake-build-debug --target wiredtiger_shared wt --parallel $(nproc)

vWeaver_ermia (needs dbcore/burt-hash.cpp generated first if it doesn't exist yet -
python3 patches/vweaver_burt_hash_gen.py > <workspace>/vWeaver_ermia/dbcore/burt-hash.cpp
- and hugepages reserved, see section 5):
    CC=clang CXX=clang++ \
    CXXFLAGS="-I/usr/include/c++/13 -I/usr/include/x86_64-linux-gnu/c++/13" \
    LDFLAGS="-L/usr/lib/gcc/x86_64-linux-gnu/13" \
    cmake -S <workspace>/vWeaver_ermia -B <workspace>/vWeaver_ermia/build \
        -DCMAKE_BUILD_TYPE=Release -DCMAKE_BUILD_PARAM=Vweaver
    cmake --build <workspace>/vWeaver_ermia/build --target ermia_SI --parallel $(nproc)

vweaver_ermia_frugal (same checkout, same prerequisites - ALSO needs
patches/vweaver_ermia_frugal.patch applied first, or `-DHYU_SKIPLIST` won't even link, see
section 5):
    CC=clang CXX=clang++ \
    CXXFLAGS="-I/usr/include/c++/13 -I/usr/include/x86_64-linux-gnu/c++/13" \
    LDFLAGS="-L/usr/lib/gcc/x86_64-linux-gnu/13" \
    cmake -S <workspace>/vWeaver_ermia -B <workspace>/vWeaver_ermia/build_frugal \
        -DCMAKE_BUILD_TYPE=Release -DCMAKE_BUILD_PARAM=Eval_skiplist
    cmake --build <workspace>/vWeaver_ermia/build_frugal --target ermia_SI --parallel $(nproc)

BenchBase (from <workspace>/benchbase):
    mvn clean package -P postgres -DskipTests \
        -Dmaven.compiler.source=21 -Dmaven.compiler.target=21 -Djava.version=21
    tar xzf target/benchbase-postgres.tgz -C target

Or just run `python3 scripts/compare_engines.py` without --skip-build - every engine's

8. PLOTTING
-------------

    python3 scripts/plot.py <output-root>/run_<timestamp>

The script detects comparison, benchmark-suite, HTAP analytical, skew-sweep, and raw
CSV directories automatically. Omit the directory only to plot recognized CSVs in the
current directory. It needs the venv's pandas/matplotlib - either activate it
(`source scripts/.venv/bin/activate`) or invoke its interpreter directly
(`scripts/.venv/bin/python3 scripts/plot.py ...`).

Every figure is written as both PDF and SVG into <run-dir>/plots/. Figures produced:

  tpcc_throughput_by_engine       TPC-C New-Order/sec, one bar per engine
  ycsb_throughput_by_engine       YCSB A-F ops/sec, grouped bars per workload x engine
  memory_by_engine                Peak measured memory per workload x engine (PostgreSQL
                                  uses its service cgroup total when available)
  summary_all_workloads            Every workload's primary metric, log-scaled, one chart
  threads_sweep_<workload>         Throughput vs. thread count, one line per engine (and
                                  per GC variant where applicable) - one file per workload;
                                  HTAP emits separate ..._gc_on/..._gc_off files so the
                                  two GC states are never overlaid
  gc_on_vs_off                     GC-on vs GC-off throughput, batstore/postgres only (the
                                  only two with a real toggle - see section 5)
  ycsb_e_scan_latency              YCSB-E scan-op latency (p50/p95/p99), across engines
  batstore_tpcc_olap_scan_latency      BatStore-only: its always-on concurrent OLAP-scan-sweep
                                  thread's latency vs. staleness/delay (HTAP-mode data
                                  specific to BatStore, not comparable to the other engines'
                                  plain-OLTP TPC-C run in this harness)
  htap_interference                 OLTP throughput drop (%) under concurrent CH-benCHmark
                                  analytics (htap_q1/htap_q6) vs. plain TPC-C, per engine
  ch_query_latency                  CH-benCHmark Q1/Q6 analytical query latency, across
                                  engines that support it

Most bar-chart-style figures (everything except the threads_sweep_* ones, which use every
thread point) are drawn from a "reference slice": the LARGEST thread count present in the
manifest, and gc="on" for engines that support toggling GC / "n/a" for the ones that
don't (never "off", so a bar chart never silently shows the GC-disabled number as if it
were the default). Every such figure's title says which thread count it's pinned to.
